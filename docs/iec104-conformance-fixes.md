## 一、背景

审计发现协议层与引擎层**并非完整符合 IEC 60870-5-104 标准**，而是"电力 SCADA 常用业务子集"的可用实现。本报告记录已修复的 13 项问题（9 项主修复 + QA 独立验证阶段揪出的 4 项）。

## 二、P0 严重（影响与真机互操作）

### 1. 时钟同步 ASDU 多写 7 字节
| | |
|---|---|
| 位置 | `core/protocol/asdu.py` `build_clock_sync` / `build_clock_sync_ack` |
| 根因 | 同一 InformationObject 同时设置 `data=time_tag.to_bytes()` 与 `time_tag=`，`encode()` 两处均写入 |
| 修复前 | **23 字节**（时间被写两遍，第三方设备可能拒收） |
| 修复后 | **16 字节**（标准值），hex 中时标仅出现一次 |
| 影响面 | 主站发送 + 子站确认双向都曾受影响 |

### 2. 组召唤 QOI 与响应 COT 非标
| | 修复前 | 修复后（标准） |
|---|---|---|
| 组召唤 QOI（主站发） | 组号 1-16 | `20 + 组号` = **21-36** |
| 召唤响应 COT（子站回） | 41-63 | **20**（站）/ **21-36**（组） |
| 累计量响应 COT | 走 41+ | **37**（总）/ **38-41**（组 1-4） |
| 主站接收判定 | `cot >= 20`（过宽） | C_IC_NA_1 仅 20/21-36；C_CI_NA_1 仅 37/38-41 |

> 说明：修复前主从站"自洽"故自测互通，但与真机不通——发 QOI=1 属非法值，回 COT=41 在标准中是"第 4 组累计量请求"。

## 三、P1 过程完整性

### 3. 文件传输握手闭环
- 主站收到 `F_FR_NA_1` / `F_SR_NA_1` 时**自动回** `F_FR_NB_1` / `F_SR_NB_1`；收到 `F_LS_NA_1` 回 `F_AF_NA_1`
- 子站 `F_LS` 状态由 0 改为 **1**（最后的节）——原值导致主站永不判定 COMPLETED
- 子站支持文件选择 **qualifier=4**（原静默忽略）
- 结果：完整上传流程可跑通至 COMPLETED 并触发 `_on_file_received`（新增端到端测试）

### 4. P/N 否定确认落到标准位置
- `ASDU` 新增 `pn` 字段（COT **bit6**），encode `(cot & 0x3F) | 0x40`、decode 解析
- 子站 4 处否定确认不再篡改命令数据字节 bit7（该位在单/双/升降命令中是 S/E 选择位，原实现污染了 SBO 语义）
- 主站按 `pn` 判定否定确认

### 5. 复位进程 / 参数命令过程
- 核实标准后确认：`C_RP_NA_1` 为 ACT→ACTCON，**无 ACTTERM** → 修正**主站**判定（原主站错误等待永不到来的 ACTTERM）
- `P_ME_NA/NB/NC` → 回 ACTCON 并记录"已装载"；`P_AC_NA_1` 已装载→ACTCON + **ACTTERM**，未装载→否定确认（pn=1）

## 四、P2 缺失能力补齐

### 6. TypeID 58-64（带 CP56Time2a 的控制命令）
补齐 7 个类型：`C_SC_TA_1`/`C_DC_TA_1`/`C_RC_TA_1`/`C_SE_TA_1`/`C_SE_TB_1`/`C_SE_TC_1`/`C_BO_TA_1`，含 builder、解码注册、子站处理（ACTCON 同类型回显）、主站发送方法。
round-trip 实测：C_SC/DC/RC_TA_1=**17B**，C_SE_TA/TB_1=**19B**，C_SE_TC_1=**21B**，C_BO_TA_1=**20B**。

### 7. COT 42/43/44/45 未知类型/原因/地址应答
- 新增 `ASDU.decode_header()` 容错头解析（TypeID 未知时仍可提取 type_id/COT/CA）
- 子站：未知类型→**COT 42**、未知 COT→**43**、公共地址不匹配→**44**，且**保持连接不中断**
- 主站：优雅记录 + 触发事件，不误判为业务响应

### 8. 定时器与流控对称化
- **t0 归属核实**：t0 是连接建立超时，属**主站**职责 → 新增 `use_t0` 开关（子站传 `False`），删除子站误导性分支
- **t1 覆盖 U 帧**：新增 `on_u_frame_act_sent()`，STOPDT ACT / TESTFR ACT 发送时也启动 t1
- **主站 k 窗口耗尽**：由"直接抛异常"改为**等待至多 t1 再抛**（与子站对称）；文件传输 4 个发送方法同步接入
- **失序策略统一**：按标准（失序应关闭连接）两侧均断链；主站新增 `disconnect()` 区分"断开后重连"与"彻底停止"

### 9. 时标与编码缺陷
- **CP24 时标类型**：编码本就正确（13B 为标准值）；真缺陷在**解码**——TA 类被构造成 `CP56Time2a`，导致 round-trip **13→17 膨胀**。已修，现稳定 13→13
- **M_ME_ND_1**：编码由 12B 改为 **11B**（去品质 QDS，符合"无品质"语义）
- **保护事件**：新增 `ProtectionEvent.to_bytes()`，`M_EP_TA/TB/TC_1`=**15B**、`TD/TE/TF_1`=**19B**，不再抛 TypeError

## 六点五、联合调试（2026-09-26）新发现并修复的问题

真机联调方式：`app.py --mode slave --no-browser --port 24040` + `app.py --mode master …`
两端各自打开 Web UI，用 `qa_verify/qa_joint_debug.py` 逐项下发召唤/遥控/时钟同步/累计量召唤，
并**逐帧解码**核对 IOA、COT、S/E、类型标识。

### A. 召唤应答把非连续 IOA 打包进一帧 SQ=1 → 主站静默错址（P0）

| | |
|---|---|
| 位置 | `core/engine/slave.py` `_send_interrogation_data`（YX/DP/YC/YM 四路）+ `_handle_counter_interrogation` |
| 现象 | 点表 YX={1, 2001, 2002} 时，子站把 3 个点打成**一帧** SQ=1（首 IOA=1, num=3），主站解出 **IOA=1/2/3** |
| 根因 | 标准规定 SQ=1 只发送帧内首个对象 IOA，其余按 +1 推得（`ASDU.encode` 一致实现）；而 `build_*_sequence` 的契约要求"IOA 连续"，调用方却直接按 `_MAX_*_PER_FRAME` 切片，未做连续性判断 |
| 影响 | 遥信/遥测值被写到**不存在的 IOA** 上，现场点表几乎都非连续 → 召唤数据整体错位且无任何报错 |
| 修复 | 新增 `_split_contiguous(batch, max_per_frame)`：按 IOA 升序切分连续段并限长，四路召唤 + 累计量召唤全部改走该函数 |
| 证据 | 修复前主站解出 `IOA=[1, 2, 3]`；修复后 `IOA=[1, 2001, 2002]`（YX 分成 [1] 与 [2001,2002] 两帧） |

### B. 召唤里重复上送已变位遥信、且类型不带时标（P1）

| | |
|---|---|
| 位置 | `core/engine/slave.py` `_send_interrogation_data` 末尾的"带时标单点遥信 (SOE)"块 |
| 现象 | 变位过的遥信在一次召唤中出现**两次**（同 IOA），第二次仍为 `M_SP_NA_1`，非 SOE |
| 根因 | 该块用 `change_count > 0` 筛选后调用**不带时标**的 `build_single_point_sequence`，代码注释亦自认占位（"需要带时标的类型，但该 builder 不支持"） |
| 修复 | 删除该块：召唤应答只上送当前值；带时标 SOE（`M_SP_TB_1`, COT=3）由 `send_spontaneous_yx` 在变位时上送，职责不重叠 |
| 证据 | 子站侧真 TCP：变位后召唤 `IOA=[1, 2001, 2002]` 无重复、类型/COT 全为 `(M_SP_NA_1, 20)` |

回归测试：`tests/test_slave_interrogation_packing.py`（5 项切分单测 + 3 项真 TCP 端到端），
端到端均已**证伪**验证（还原旧行为后分别复现 `IOA=[1,2,3]`、IOA 1 重复出现、双点被当单点上送）。

### C. 命令执行后不反映被控点状态（P1，真机语义缺失）

| | |
|---|---|
| 位置 | `core/engine/slave.py` 单/双命令与设点命令的执行分支 |
| 现象 | 遥控执行后同 IOA 遥信不变位、不上送；遥调执行后遥测值不变、不上送（双命令、设点连实时库都不写） |
| 真机行为 | 遥控成功 → 同 IOA 遥信立即变位并带时标上送（COT=3）；遥调成功 → 同 IOA 遥测更新并上报 |
| 修复 | 新增 `_reflect_command_result()`：按**点表声明**选择上送类型（单点 → `M_SP_TB_1`、双点 → `M_DP_TB_1`、遥测 → `M_ME_TF_1`），值未变化或点表无该点时不上送（避免冗余报文与幽灵点）；双命令补上 `update_yk` 记录 |
| 有意不做 | 升降命令（调节步）不联动——它改变的是档位（真机 `M_ST_NA_1`），本工具点表未建模步位置点 |
| 回归 | `tests/test_command_feedback.py`（5 项真 TCP 端到端，含"无配对点不上送""值未变不重复上送"），已证伪（关闭联动后 4 项失败） |

### D. 召唤把双点遥信同时按单点与双点重复上送（P1）

| | |
|---|---|
| 位置 | `core/engine/slave.py` `_send_interrogation_data` 遥信分流 |
| 现象 | 点表声明为双点的遥信，先被 `M_SP_NA_1` 上送一次，又因 `double_state` 真值判断被 `M_DP_NA_1` 上送一次（同 IOA 两条）；且 `double_state == 0` 的双点被真值判断漏掉 |
| 根因 | 单点批次不做类型过滤（全量收进 `yx_batch`），双点批次用 `if yx_data.double_state` 而不是类型判断 |
| 修复 | 按点表声明分流：`point_type == DOUBLE` → `M_DP_NA_1`（状态 0/1/2/3 原样上送），否则 → `M_SP_NA_1`；每点只上送一次 |
| 证据 | 修复前召唤单点帧含 `IOA=[1, 2002, 2003]`（2002/2003 为双点）；修复后单点帧仅 `IOA=[1]`、双点帧 `IOA=[2002, 2003]`（值 2 与 0 均正确上送） |

## 六点六、类型覆盖补齐（2026-09-26，接口层「全部实现」）

审计方式：以 `TypeID` 枚举为基准，逐项核对**解码注册 / 构造器 / 子站处理 / 主站处理**四列。
补齐前的问题不是"标准类型缺失"，而是**"能解不能发"的半实现**：解码表里有的类型，`ASDUBuilder` 里没有对应构造器，
于是子站无法模拟这些来报（也无法用于反向测试）。

| 补齐项 | 类型 | 说明 |
|---|---|---|
| CP24 短时标变体（8 个） | M_SP_TA_1(2)、M_DP_TA_1(4)、M_ST_TA_1(6)、M_BO_TA_1(8)、M_ME_TA_1(10)、M_ME_TB_1(12)、M_ME_TC_1(14)、M_IT_TA_1(16) | 原只有 CP56 变体可发；CP24 时标 (3B) 必须保持，不能膨胀为 CP56 (7B) |
| 继电保护设备事件（6 个） | M_EP_TA_1(17)、M_EP_TB_1(18)、M_EP_TC_1(19)、M_EP_TD_1(38)、M_EP_TE_1(39)、M_EP_TF_1(40) | 事件值/动作时间/成组启动/成组输出四类字段 |
| 成组单点带状态检出（2 个） | M_PS_NA_1(20)、M_PS_TB_1(71) | 每对象最多 8 点，状态位与检出位分离 |
| 无品质变体（2 个） | M_ME_ND_1(21)、P_ME_ND_1(109) | 仅 2 字节归一化值，无 QDS |
| 位模式测试命令 | C_TS_NB_1(108) | 101 类型，位模式无时标 |

回归测试：`tests/test_protocol_type_coverage.py`（20 项，含"每个 build_* 产物必须可解码"的护栏用例）。
边界说明：比特串信息（M_BO_*）按标准不带品质描述词，故构造器不提供 `quality` 参数。

**引擎侧说明（有意为之）**：子站/主站的实时上送统一使用 **CP56Time2a 变体**（与 104 实践一致，
CP24 属 101 链路风格）；CP24 构造器用于负向测试与 101 风格报文。若需子站按 CP24 上送，
应在点表增加"时标风格"配置项后接入，属独立需求。

## 六点七、机制层补齐（2026-09-26，独立审计 + 实测复核）

对 `TypeID` 四列矩阵与机制层逐项审计后，又补齐 5 项机制缺口。**其中 1 项审计结论经实测被推翻**，
一并记录，避免后人重复"修复"不存在的问题。

| # | 机制 | 修复前 | 修复后 | 证据 |
|---|---|---|---|---|
| 1 | **T 试验位（COT bit7）** | 编码恒 0、解码丢弃 | 编码/解码保留 T 位；子站对 T=1 的测试命令**回显 T=1**；主站**不把 T=1 的监控报文入库**（标准：试验报文非真实数据） | 往返测试 + 子站回显 + 主站跳过入库，3 项用例；证伪：丢弃 T 位后 3 项全失败 |
| 2 | **读未知 IOA 应答** | 静默无应答 | 回 `COT=45`（未知信息对象地址），类型保持 C_RD_NA_1 | 真机联调场景 12c：子站应答 COT=[45]、type=[102] |
| 3 | **C_CD_NA_1 延时获得** | 固定回 100ms 示例值；解码为原始字节，子站读不到请求值 | 解码为 `DelayCommand`；按请求延时推迟应答并回显实际值（上限 10s 防挂死） | 用例断言 `elapsed>=0.25s` 且应答回显 300ms |
| 4 | **主站累计量 CP24 变体** | `_process_asdu` 只列 `M_IT_NA_1`/`M_IT_TB_1` | 补 `M_IT_TA_1`——真机 CP24 时标电度不再被静默丢弃 | 用例：喂 M_IT_TA_1 后主站实时库值正确 |
| 5 | **ASDU 长度上限** | `MAX_ASDU_LENGTH=253` 定义但未强制 | `ASDU.encode()` 超限抛 `ValueError` | 用例：200 对象 M_SP_NA_1 触发异常 |

### 被推翻的审计结论（实测证据）

- **"M_ME_ND_1 解码品质读到下一对象首字节"** —— **不成立**。`NormalizedValue.from_bytes`
  有长度保护（`types.py:419`：`len(data) > offset+2` 才读品质字节），而解码器只传入 2 字节切片，
  故品质恒为 GOOD。实测：构造两个 M_ME_ND_1 对象（IOA 100/101，前者的 IOA 最低字节 0x64
  恰好是可疑品质位）解码后品质仍为 GOOD。已保留显式补 0 品质字节（防御 + 语义直白），
  并在代码注释写明"安全性来自长度保护"。

### 判为"非缺陷"或"有意保留"的项

| 项 | 结论 |
|---|---|
| 公共地址 CA 长度固定 2 字节 | **IEC 60870-5-104 规定 CA 为 2 字节**（101 才可配 1/2），引擎恒用 2 字节是正确的；`ca_length` 参数用于 101 风格解析 |
| 重复地址检测（IOA/CA 去重） | 标准未强制；作为测试工具保留原样（可由 `drop/corrupt` 注入构造异常场景） |
| 参数命令主站侧状态跟踪 | 记为遗留（见第七节），主站目前只记录日志 |
| 继保事件/成组单点数据模型 | 构造器已备（可发测试报文），但点表未建模此类点，**未**接入自动上送 |

| **非标准 TypeID 编号** | `M_PS_TB_1=71`、`C_TS_NB_1=108`、`P_ME_ND_1=109`、`F_FR_NB_1=128`、`F_SR_NB_1=129` 占用了标准保留号或超出 127 范围 |
| **`wrong_cot` 注入** | 已于 2026-09-26 落地：`SlaveEngine._reply_cot()` 把应答（命令确认/召唤确认·数据·结束/时钟同步确认）的 COT 整体 +1，Web UI「返回错误COT」开关与 `errors.wrong_cot` 配置贯通；自发上送与标准错误应答（42/43/44）不参与注入 |
| **文件传输 F_LS 语义** | 功能已闭环（status=1，主站接受 {1,2}），但该八位组在标准中的严格定义（校验和 CHS 与 QLS 的取舍）建议与目标设备实测核实 |
| **背景扫描** | IEC 104 不适用（仅 101） |
| **参数命令"先删后写"顺序** | 未做设备级验证，建议对真实设备联调时观察 |

## 八、结论

修复后，协议层与引擎层在**常规业务与真机互操作**层面已对齐标准：召唤（站/组/累计量）、时钟同步、遥控选择-执行、参数装载激活、文件传输全流程、否定确认、错误应答（COT 42/43/44）均按标准实现，且主从站行为对称。

**仍未达标的是"型式试验/一致性认证"级别的完整覆盖**——缺 TLS、冗余，以及少数非标准 TypeID 编号。若需用于正式入网检测，建议以本文第七节为输入，对照目标检测机构的用例清单做逐项确认。
